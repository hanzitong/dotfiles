# Claude の日本語の返答の書き方（すべてのプロジェクトのためのルール）

このルールは、Claude がユーザーに返す日本語の返答に当てはめる。Claude が日本語の文書（仕様書、ADR など）を書くときも、このルールの決まりに従う（`~/.claude/rules/japanese-document-style.md`）。

- 日本語を、論理的に、誤解がないように書く。
- 動詞を使うときは、その動作主（主語。誰が、何が）を書く。
- 動詞を使うときは、できるだけ、その修飾語（どこに、どこから、何を、いつ、どのように）も書く。主語だけでは足りない。
  - 例: 「ログを出します」→「`_report_thread_death` が、ログを出します」（まだ足りない）→「`_report_thread_death` が、標準出力に1行のログを出し、標準エラーにトレースバックを出します」。
  - 例: 「確かめました」→「Claude が、`config_loader.py` を読んで、ほかのファイルから import されていないことを確かめました」。
- コードの中の物（変数、データの構造、関数、スレッド、HTTP のエンドポイントなど）を指すときは、たとえの言葉（「入れ物」「置き場」「窓口」「口」など）で言い換えない。何を入れておくか、何をするかと、型や種類（`list[str]`、`dict[str, int]`、`queue.Queue[str]`、関数、スレッド、HTTP のエンドポイントなど）を書く。
  - 例: 「返事の入れ物」→「返事を入れておく `list[str]`」。
  - 例: 「`robot_action_process` が文を取る口」→「`robot_action_process` が文を取るための HTTP エンドポイント `GET /get_customer_answers`（`prompt_process` が受ける）」。
  - 理由: たとえの言葉では、それが list か dict かキューか、変数か関数か HTTP のエンドポイントかが分からない。読み手は、コードのどの物を指しているのかを推測しなければならない。
- list、dict、set、tuple、キューなどの、値をまとめて持つ型は、要素の型まで、型ヒントの形で書く（`list[str]`、`dict[str, int]`、`queue.Queue[str]`）。「リスト」「list」「辞書」「キュー」だけで書かない。
  - 例: 「空のリストを返す」→「`prompts` が空の `list[str]` である `PromptMessage` を返す」。
  - 理由: 「リスト」だけでは、要素が文字列か、dict か、別のクラスかが分からない。読み手は、受け取った値の扱い方を、コードを読んで確かめなければならない。
  - 例外: 要素の型をコードで確かめられないときは、推測で書かず、「要素の型は未確認」と書く。
- HTTP のエンドポイントは、メソッドとパスの組（`GET /get_customer_answers`）で書き、そのエンドポイントを受けるプロセスを添える。
  - 理由: パスだけでは、GET か POST かが分からない。受けるプロセスがないと、どのサーバーに送るのかが分からない。
- コードの中に名前があるもの（プロセス、クラス、関数、変数など）は、日本語に訳さず、コードの名前で書く（「ロボット動作プロセス」→「`robot_action_process`」）。
  - 理由: 訳した名前では、読み手が、コードのどれを指すのかを確かめなければならない。訳し方が揺れると、別の物を指すようにも読める。
  - 例外: ADR の本文では、関数、変数、定数の名前を書かず、adr スキルの「ADR の本文に、詳細な実装を書かない」に従う。プロセスの名前は、ADR でもコードの名前で書いてよい。この例外の後半は Claude の解釈であり、ユーザーには確かめていない。
- プロセスやスレッドの間のやりとりを、人にたとえた動詞（「教える」「伝える」「知らせる」「頼む」など）で書かない。送る側、受け取る側、手段（HTTP ならメソッドと URL、キュー、共有の変数など）、受け取った側が書き換える変数を書く。
  - 例: 「ロボット動作プロセスに教えられた締め切りの時刻を1つ持っていて、」→「`robot_action_process` から HTTP の POST（`/deadline`）で受け取った締め切りの時刻を、`float` のインスタンス変数に1つ持っていて、」（例の中の URL と型は、書き方を示すための仮のもの）。
  - 理由: 「教えられた」では、どのプロセスが、どの手段で、どの変数を書き換えたのかが分からない。読み手は、HTTP か、キューか、メソッドは何かを、コードを読んで確かめなければならない。
- 1つの文に、関係の違う2つ以上の情報（決めたことと、その効果など）を詰め込まない。「〜し、」「〜で、」でつなぎたくなったら、文を分け、2文目の頭に、関係を表す言葉（「こうすると」「そのため」）を置く。
  - 理由: 情報を1文に詰め込むと、読み手は、情報どうしの関係（理由、結果、条件）を読み取れない。
  - 悪い例: 「終了判定には26Bのお世話用VLMに画像を1枚渡す方式にし、GPUのメモリは増えません。」
  - 良い例: 「終了判定には２６Bのお世話用VLMに画像を１枚渡す方式にします。こうするとGPUのメモリ使用量は増えません。」
- 「増える」「減る」「変わる」の主語には、物（メモリ、ディスク、CPU）ではなく、量（使用量、時間、回数、大きさ）を書く（「GPU のメモリが増える」→「GPU のメモリ使用量が増える」）。
  - 理由: 物の名前を主語にすると、物そのもの（取り付けたメモリ）が増えるとも読める。
- 説明の前に、必ず前提を説明する。ユーザーを、その話について何も知らない、外から来た人だと思って説明する。
  - 前提として整理して伝えること: 何の話か、登場するもの（プロセス、ファイル、関数など）、それぞれの役割、いまどういう状況か。
  - 前提を伝えてから、本題の説明に入る。
  - 例外: 返答の末尾の「先回り解説」では、前提を原則1文にする（`~/.claude/rules/proactive-explanation.md`）。
