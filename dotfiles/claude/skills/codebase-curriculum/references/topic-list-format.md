# 学習トピックの一覧の md の書式

このファイルは、`codebase-curriculum` スキルの段階1で、Claude（または執筆のエージェント）が、学習トピックの一覧の md を書くときの書式である。読み手は、教材で学ぶユーザー本人で、この一覧から学ぶトピックを選ぶ。

## 文書の構成

文書は、次の節を、この順に置く。

1. **この文書について**
   - 何の文書か、どう作ったか（どのディレクトリを読んだか、範囲の外にしたもの、出現回数の数え方、どのコミットの時点か）。
   - 行番号は、コードの編集で変わりうること。
   - 「選定の基準」の小節: SKILL.md の基準 A〜F の表と、このコードベースで使った線（例: A は出現回数が何回以上か）。
   - 「読み手の習熟」の小節: 読み手が申告した、分かっていること、慣れていないこと、重点的に理解したいこと。読み手が分かっているものは、独立したトピックにせず、「一覧から外した候補」に置く。重点的に理解したいトピックには、表の「指定」の列と詳細に「重点」の印を付け、学ぶ順の案で早めに置く。
     - 理由: 読み手が既に分かっているトピックは、選ぶ手間を増やすだけである。重点の印は、読み手が限られた時間で、どこから学ぶかを決める手がかりになる。
   - 使い方: 各トピックの `- [ ] 学ぶ` に `x` を付けて選ぶこと。
2. **全体の地図**: 題材のシステムが何か、プロセスとスレッドの構成、外部（範囲の外のサーバー、機器）とのつながり。教材の前提として短く書く。
3. **ユーザーが指定したトピックとの対応**: ユーザーが挙げた項目ごとに、対応するトピックの id。
4. **分野ごとの節**: 設計判断（ADR）の節を最初に置き、そのあとに、言語の文法、組み込み関数、標準ライブラリ、外部のライブラリ、並行処理、通信、アーキテクチャと設計、デザインパターン、分野の知識、起動と環境（Docker、シェル）、テスト、エラー処理とログ、などの節を、材料に合わせて置く。
5. **学ぶ順の案**: 前提の関係に沿った段階ごとの id の並び。
6. **一覧から外した候補**: 外した理由を、当てはまらなかった基準の形で書く。

## 分野ごとの節の書き方

各節は、まず表で一覧を示し、そのあとで各トピックの詳細を書く。

表の列:

| 選ぶ | id | トピック | 難しさ | 出現回数 | 選定の基準 | 指定 |
|---|---|---|---|---|---|---|

- 「選定の基準」の列には、当てはまる記号を並べる（例: `A, B, F`）。
- 「指定」の列には、ユーザーが指定したトピックに印を付ける。

各トピックの詳細は、次の項目を、この順に書く。

- 見出し: id とトピック名。
- `- [ ] 学ぶ`
- 何か: 1〜2文。
- このコードベースでの使われ方。
- なぜ大事か: 知らないと起きる誤りを含める。
- 扱う細目: 例えば `queue.Queue` なら `put()`、`get(timeout=...)`、`get_nowait()`、`queue.Empty`。
- 代表の箇所: リポジトリからの相対パスと行番号、コード片を1行。2〜3個。別々のサブシステムから選ぶとよい。
- 先に学ぶトピック: id。
- 関係する ADR: あれば。
- 選定理由: 当てはまる基準の記号と、このトピックに固有の根拠の事実を、2〜3文で書く。
- 設計判断（ADR）のトピックでは、あわせて、何を決めたか、比べた選択肢と諦めたこと、その判断がコードのどこに現れるかを書く。

## 選定理由の良い例と悪い例

良い例（数と ADR の番号は、書き方を示すための仮のもの）:

```markdown
- 選定理由: A, B, F。`queue.Queue` は、範囲の中の 14 ファイルに 52 回出てくる。assembly_system と coffee_system の両方で、HTTP のサーバーのスレッドから実行のスレッドへ依頼を渡す方式に使われている（ADR-0014）。ユーザーが「queue.Queue のよく使われるメソッド」を指定した。
```

悪い例（根拠の事実がない）:

```markdown
- 選定理由: よく使われていて重要なため。
```
